# First production deployment: single KVM node

Status: production Compose, shared infra example, replicated/sharded-ready ClickHouse schema, frontend image, CI image publishing, a GHCR deployment bundle and an interactive one-command installer are implemented in the feature branch. This document still tracks the remaining release checks; `deploy/docker-compose.yml` remains the development stack. See [production-deployment.md](./production-deployment.md) for the implemented startup flow.

Traffic is purchased before it reaches this service. Temporary MongoDB, ClickHouse or Redpanda failure must not turn an otherwise routable request into an HTTP error. Routing uses the latest valid local campaign snapshot and an operator-configured destination or trafficback fallback; analytics failures are counted and alerted. If no valid campaign configuration or safe fallback has ever been loaded, the service cannot invent a redirect target. Production activation must verify that every active campaign has a fallback.

Destination probes run in the background. Confirmed-unhealthy destinations are removed from selection, and an all-unhealthy campaign uses its configured trafficback rather than returning 503. Add failure/recovery thresholds so one transient probe does not flap routing; verify that the probe tests a representative URL without following a misleading redirect chain. Probe latency must never enter the click request path.

## Host and ownership

- Target: Debian 13 (trixie), x86_64 KVM VPS, 16 vCPU, 28 GB RAM, 180 GB NVMe-backed storage.
- Host packages: Docker Engine, Docker Compose plugin and system utilities. Go, Node.js, databases, Nginx and Certbot run only in containers. The server downloads a versioned GHCR deployment bundle; it does not clone the repository.
- `/opt/infra` owns shared Nginx, Certbot, certificates and ACME webroot. `/opt/traffoflex` owns the extracted deployment bundle and its production Compose project. `/opt/projects` is reserved for other apps. `/opt/backups/traffoflex` holds backups outside application containers.
- The shared external Docker network is `proxy`, created independently of any project. The TraffoFlex Compose project owns a separate `traffoflex_internal` network. MongoDB, ClickHouse and Redpanda join only the private network. Nginx and the four web services join `proxy` as needed; all application and database ports stay unpublished. The only host-published HTTP ports are Nginx 80 and 443; SSH remains on 22.
- Docker on one VPS is a single failure domain. Three Redpanda containers on that VPS would not provide host-level high availability.

## Verified application routing

| Domain | Existing service and port | Existing paths |
| --- | --- | --- |
| Configured tracker domain | `traffic-service:8080` | `/c/{campaignSlug}`, `/go/{campaignPublicId}`, `/r/{publicToken}`, `/tb/{campaignSlug}` |
| Configured postback domain | `postback-service:8081` | `GET /pb/{network}`, `POST /api/postbacks` |
| Configured admin domain | `admin-frontend:5173` in development; `api-service:8070` | Frontend routes at `/`; backend routes under `/api` |

Production Nginx routes `/api/` on the configured admin domain to `api-service:8070`, and other app paths to the built frontend. The frontend uses a same-origin `/api` base path. Replace the current Vite development container with a multi-stage build and static-file serving container; do not expose the Vite dev server. Keep the three Go multi-stage builds, and pin production images rather than installing Go or Node on the host.

Public postbacks require a configured secret in a MongoDB postback template for their network. `GET /pb/{network}` checks that network; `POST /api/postbacks` currently checks the template network `api`. Missing or incorrect secrets return 401; a template lookup failure returns 503. Configure a unique secret before sending partner postbacks. GET secrets appear in URLs, so the production Nginx access log for the configured postback domain must omit the query string, and partner integrations should use POST where possible.

The current client-IP resolver trusts forwarding headers only when the TCP peer matches `TRUSTED_PROXY_CIDRS`. Configure a narrow, stable Nginx source address on the shared network and trust only that address. Nginx must overwrite inbound `X-Forwarded-For` with the actual peer IP rather than forwarding a visitor-supplied chain, and set `Host`, `X-Real-IP` and `X-Forwarded-Proto`. Test spoofed headers and requests through Nginx. Do not change attribution fields without a failing test.

## Shared infra stack

Add `deploy/infra/compose.yml`, `.env.example`, `nginx/nginx.conf`, `nginx/conf.d/traffoflex.conf.example` and Certbot support files. Infra Compose contains only official Nginx and Certbot images. Both use bind mounts copied under `/opt/infra`: `./letsencrypt:/etc/letsencrypt` and `./certbot-www:/var/www/certbot`. Nginx alone publishes 80/443 and reaches TraffoFlex services by Docker DNS, never via host loopback or the VPS public IP.

- Start with an HTTP-only Nginx configuration that serves `/.well-known/acme-challenge/` from the shared webroot. An HTTPS configuration cannot load before its certificate files exist.
- Document the first `certbot certonly --webroot` issuance for all three domains, then enable the 443 virtual hosts and reload Nginx. Redirect ordinary HTTP requests to HTTPS after issuance.
- Document `docker compose run --rm certbot renew` followed by `docker compose exec nginx nginx -s reload`, with a host systemd service/timer example. Certbot remains a container; no host Certbot package.
- Enable Nginx access/error logs and rotate them with Compose `json-file` limits. Keep the tracker proxy path minimal, use upstream keepalive, and avoid an unapproved traffic rate limit or heavy request processing.
- Give Nginx an HTTP healthcheck that validates its configured listener, not merely process existence. Check certificate issuance and renewal in deployment validation.

## TraffoFlex production stack

Add `deploy/docker-compose.prod.yml` and `.env.production.example`; preserve the existing development Compose file and targets. Include `traffic-service`, `postback-service`, `api-service`, a production frontend, one Redpanda broker, one ClickHouse and one authenticated MongoDB. Attach only the four web containers to `proxy`. Use `restart: unless-stopped`, persistent named volumes for all three data services, Compose healthchecks, and per-container `json-file` log rotation (`max-size: 20m`, `max-file: 5`). Use dependency health conditions only for services that cannot start correctly before their dependencies.

Initial purchased traffic is expected at 10,000–50,000 clicks/day. Keep the earlier 1,000-click/s figure as a burst or stress-test ceiling, not a daily forecast. Click analytics use hour and UTC-day rollups retaining report dimensions. Reports preserve second boundaries with raw partial-hour reads; background cap/ROI checks combine complete hours with the raw boundary hour.

- Redpanda: one broker, replication factor 1, initial 2–3 GB RAM and about 2 vCPU. Keep existing topics and event payloads. The current ClickHouse ingestion SQL hard-codes three broker addresses in five queue tables; provide a production-specific broker setting or generated SQL while reusing the existing schema. Validate topic creation and ClickHouse ingestion end to end.
- ClickHouse: one authenticated instance with an embedded, persisted single-node Keeper, one shard and one replica, persistent volume, healthcheck and initial 6–8 GB memory ceiling. The production image renders the existing schema as `Replicated*MergeTree` local tables and `Distributed` public tables, retaining the existing materialized views. Keep HTTP 8123 and native 9000 private. Additional shards require a deliberate ingestion/query and data-placement rollout; existing data does not rebalance automatically. Do not enable a destructive data TTL until event sizes and retention needs have been measured.
- MongoDB: one authenticated instance, persistent volume, authenticated healthcheck and an initial WiredTiger cache target of 2–3 GB. Use application credentials distinct from the root/init credential. Keep 27017 private.
- Web services: initial memory budgets of 1–2 GB for traffic, about 1 GB each for postback and API, 256–512 MB for frontend; allow 256–512 MB for Nginx. Leave at least 6–8 GB for the OS, filesystem cache, Docker and spikes. Avoid tight CPU caps at first; confirm budgets with `docker stats` and load tests.
- Use existing `/readyz` endpoints for the three Go services and an HTTP check for the frontend. Report dependency failures and snapshot age separately from redirect-serving readiness. A broker or analytics database outage must be visible without taking a traffic-service instance out of rotation while it still has a valid route snapshot. Improve readiness beyond static configuration validation.
- Clicks use a durable local WAL at `CLICK_WAL_PATH` (default `/data/click-wal`) on a persistent volume. Each click is appended and synced locally before redirect; Redpanda publishing, retries and checkpoints run in the background. The WAL is bounded by `CLICK_WAL_MAX_MB` (default 2048), segmented by `CLICK_WAL_SEGMENT_MB` (default 16) and retries every `CLICK_WAL_RETRY_MS` (default 1000). When full or unwritable, the paid click still redirects, but its analytics event is lost. Monitor private `/internal/event-queues/stats`: for `clicks`, alert on `overflow_total` or `failed_total` increasing, `retry_total` increasing, `pending` growing, and `disk_bytes` approaching `max_disk_bytes`. Preserve the volume across deploys and back it up if an extended broker outage is expected. A Redpanda acknowledgement followed by a crash before checkpoint may replay the same `click_id`; downstream ClickHouse materialized views currently count such a replay again. Reconcile duplicates before treating reports as exact billing records. At 1000 clicks/s, a 2 GB WAL may fill in tens of minutes; measure real event size and alert early. Never expose the internal endpoint publicly.
- Background click duplicate auditing checks yesterday and today at startup and every 24 hours. After recovered WAL records drain, it checks their event-date range twice with a five-minute gap to allow ClickHouse ingestion. Monitor `/internal/click-audit/stats` for duplicate events, excess cost, conflicting costs, failed checks and stale results; keep this endpoint private. The audit only reports differences. Any aggregate correction must be a separate controlled operation.
- Trafficback events retain the bounded memory queue (`EVENT_QUEUE_SIZE`, default 10000). Monitor its `overflow_total`, `failed_total`, `stopped_total` and `pending` counters; these events can be lost on overflow, failed delivery or crash. Allow at least 20 seconds of container stop grace so HTTP shutdown and the bounded `EVENT_DRAIN_TIMEOUT_MS` (default 8000 ms) can complete. Benchmark local WAL fsync latency and tracker p99 at 1000 clicks/s on the target NVMe before production cutover.
- Caps and ROI refresh from ClickHouse in the background at the current `DESTINATION_CAP_CACHE_TTL_MS` interval (default 10 seconds). Watch the private `/internal/availability/stats` for `last_success_at`, `age_seconds`, `refresh_failures` and `missing_cap_checks`. A failed refresh keeps last-good values, which can become stale; caps are therefore approximate while ClickHouse is unavailable. A cap-controlled destination with no snapshot is excluded, and a campaign must have a configured trafficback if all its destinations need cap data. ROI without a snapshot uses its configured fallback ranking.
- Anti-repeat uses a local Bloom filter on the click path. Mount persistent storage at `/data/bloom` in the production traffic-service, retain `BLOOM_SNAPSHOT_PATH=/data/bloom/snapshot.gob`, and monitor private `/internal/anti-repeat/stats`. A background ClickHouse scan seeds each active stream on startup and policy changes. A stream with unavailable history or saturated filter routes to configured campaign trafficback. `BLOOM_EXPECTED_KEYS_PER_BUCKET` (default 50000), `BLOOM_FALSE_POSITIVE_RATE` (0.001), and `BLOOM_MAX_MEMORY_MB` (512) need load-based tuning. Async event loss before both ClickHouse ingestion and the next Bloom snapshot can allow a repeat after a crash.
- Mount persistent storage at `/data/cache` for `ROUTING_SNAPSHOT_PATH=/data/cache/campaigns.json`. A checksum-protected routing snapshot is saved after every successful MongoDB refresh, then restored before the first MongoDB attempt on restart. Traffic-service has no database or broker startup dependency in production Compose. With MongoDB down and a valid nonempty snapshot, it continues routing and retries MongoDB every `CAMPAIGN_CACHE_REFRESH_INTERVAL_MS` (default 30000 ms). With no usable snapshot and MongoDB unavailable, the process stays alive and retries, but `/readyz` returns 503 and no unknown campaign can redirect. All active campaigns must have a configured trafficback before the persistent cache accepts them. Monitor private `/internal/cache/stats` for snapshot mode and stale `loaded_at`; an emergency campaign disable in MongoDB cannot reach the tracker while MongoDB is unavailable.

Production configuration must have placeholders only: MongoDB root/app credentials, ClickHouse credentials, a generated JWT secret, Resend credentials, admin email, domains, internal service URLs, single-broker `EVENT_BROKERS`, and a narrow trusted proxy CIDR. Set `AUTH_ENV` to production and `AUTH_DEV_RETURN_OTP=false`. No `localhost` browser API URL, `change-me` secret or dev default may be inherited. The current `.gitignore` ignores `.env.*`, so explicitly allow `.env.production.example` while keeping `.env.production` ignored. Validate missing or example secrets at startup.

## Backups, data risks and disk

Add `scripts/backup.sh` and `scripts/restore.sh` using Docker commands so the host needs no MongoDB or ClickHouse client. Backups go to `/opt/backups/traffoflex/YYYY-MM-DD/` and include MongoDB, ClickHouse analytics/schema and critical configuration. Restore requires explicit confirmation, a maintenance window, a pre-restore backup and a documented validation step. Test restore into an isolated stack before production cutover. `docker compose down` must preserve all named volumes; never use `down -v` in ordinary deployment commands.

Redpanda currently carries click and conversion events until ClickHouse consumes them. ClickHouse is the analytics source of truth only after ingestion is verified; unconsumed Redpanda messages are business-critical. Before omitting the Redpanda volume from daily backups, implement and verify a drain/checkpoint procedure or an equivalent recovery path for in-flight events. A single broker has no replica to recover from disk loss.

Document daily backups retained for 7 days and weekly backups retained for 4 weeks, with free-space checks and cleanup limited to verified backup directories. Monitor the 180 GB disk. Keep ClickHouse retention configurable and documented; select a TTL only after measuring actual event volume and confirming the required reporting horizon. Migration or restore of existing MongoDB, ClickHouse or Redpanda data must be rehearsed before cutover: new auth and single-broker topology must not be applied in place to an unbacked-up volume.

## Operator workflow and acceptance

- Add Makefile targets `prod-up`, `prod-down`, `prod-restart`, `prod-logs`, `prod-status`, `backup`, `restore` and `smoke-prod` without changing existing development targets.
- Document the one-command installer and manual extraction of the versioned GHCR deployment bundle under `/opt/traffoflex/releases`, `.env.production.example` to `.env.production`, creation of `proxy`, separate `/opt/infra` startup, certificate issuance, TraffoFlex startup and reboot recovery. GHCR packages must be public for anonymous installation. Keep deployment reversible and use image/tag rollbacks where possible.
- Add a real production smoke test: create isolated test configuration, request a tracker redirect, verify the click reaches Redpanda and ClickHouse, send a test postback, verify the conversion in MongoDB and ClickHouse, and confirm revenue through the existing API/report route. Add fault tests that stop each data service, fill the click event queue and restart traffic-service with MongoDB unavailable; a configured campaign must still redirect, while event loss and stale snapshots remain visible. Clean test data safely and report each failed step. A `/healthz`-only test is insufficient.
- On Debian 13, document firewall access for 22/80/443 only, SSH keys, `PasswordAuthentication no` and `PermitRootLogin prohibit-password`. Never apply firewall or SSH changes automatically from deployment scripts.
- Document `docker compose ps`, `docker stats`, `docker compose logs`, `df -h`, `free -h` and `iostat`; preserve existing event producer stats. No Prometheus/Grafana stack is required for this release.
- Release gate: all relevant tests and frontend build pass; Compose configs validate; private services have no host-published ports; TLS and spoofed-IP checks pass; backup/restore is proven; smoke and failure-recovery tests pass; measured redirect latency and disk/RAM use fit the VPS.

This deployment work complements the separate first-production application gates in `implementation-plan.md`: authenticated postbacks, recoverable conversion processing, asynchronous click routing, bounded anti-repeat Bloom filter behavior and hardened admin sessions. Passing the deployment checks alone does not clear those gates.
